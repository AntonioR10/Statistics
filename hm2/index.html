HMWK 2: From Wallet Seed to Ethereum Address

Analysis of the cryptographic pipeline, hierarchical derivation, primitives and historical context.

1. The Wallet Pipeline

A wallet turns a human-friendly mnemonic into a checksummed Ethereum address through a chain of distinct steps. Each step has one job and hands its output to the next:

Step Input → Output Tool What happens
0 CSPRNG → entropy (128 or 256 bit) Random source The only truly random step. Everything after it is deterministic.
1 Entropy → mnemonic (12/24 words) BIP-39 A SHA-256 checksum is appended (4 bits for 128-bit entropy, giving 132 bits = 12 × 11 bits). Each 11-bit chunk selects a word from a 2048-word list.
2 Mnemonic (+ optional passphrase) → 512-bit seed BIP-39 / PBKDF2 PBKDF2-HMAC-SHA512 with 2048 iterations; the salt is the string "mnemonic" plus the passphrase.
3 Seed → master key and chain code BIP-32 HMAC-SHA512 of the seed, split into a 256-bit key and a 256-bit chain code.
4 Master key → account/address private key BIP-32 / BIP-44 Child derivation along the path m/44'/60'/0'/0/0 (purpose / Ethereum / account / change / index).
5 Private key k → public key Q secp256k1 Q = k · G (scalar multiplication). Result: 64 bytes (x and y coordinates).
6 Public key → address (20 bytes) Keccak-256 Hash the 64-byte public key and keep the last 20 bytes of the 32-byte digest.
7 Address → checksummed address EIP-55 Hash the lowercase hex address with Keccak-256; each letter is uppercased if the corresponding hash nibble is 8 or more.

How the steps fit together: steps 1-4 are about key management (one memorable secret recovers an entire tree of keys), step 5 is about public-key cryptography (a public identity linked to a secret that never leaves the wallet), step 6 is about hashing (a short, uniform identifier), and step 7 is about error detection (protecting humans, not the system).

2. Role of Each Standard & Cryptographic Primitive

  • BIP-39 (2013): Encodes entropy as words that are easy to write down. It converts the entropy by appending a checksum computed with SHA-256, splitting the resulting block into 11-bit chunks mapped to a dictionary of 2048 words. The seed derived via PBKDF2 uses the optional passphrase as a "25th word".
  • BIP-32 (2012) & BIP-44 (2014): Handle hierarchical deterministic (HD wallet) derivation. From a single seed, an entire tree of keys can be derived using HMAC-SHA512. BIP-44 fixes the standard paths (for Ethereum coin_type = 60), ensuring interoperability between different wallets.
  • secp256k1: The elliptic curve y2 = x3 + 7 defined over a field of about 2256 elements. It allows efficient computation of the public key Q = k · G via the double-and-add algorithm, making the inverse problem (ECDLP) intractable.
  • Keccak-256: A sponge-construction hash function. It compresses the 64 bytes of the public key into 20 bytes (160 bits) to form the address. Historical note: it differs from the NIST SHA3-256 standard because of a different padding and domain-separation convention.
  • EIP-55 (2016): A mixed-case (uppercase/lowercase) encoding mechanism based on the hash of the address. It serves to detect human typing errors without changing the actual value of the address or requiring changes to the base protocol.

3. Conceptual Distinctions

Key Generation Initial entropy

True randomness via a CSPRNG. The only non-deterministic step in the pipeline.

Key Derivation BIP-32 / BIP-44, PBKDF2

100% deterministic process: the same input always produces the same output. No new entropy is introduced.

Public-Key Crypto secp256k1

Asymmetric relationship k → Q, easy forward, intractable in reverse. Enables digital signatures.

Hashing Keccak-256

Keyless, deterministic, fixed-length one-way function with a strong avalanche effect.

Checksums BIP-39, EIP-55

Lightweight systems for detecting human transcription errors; they offer no cryptographic security.

Encoding Mnemonic, Hex, Case

Changes the visual representation of data (string/binary format) without altering its informational content.

4. SHA-2 / SHA-512 vs Keccak / SHA-3

Both are cryptographic hash functions and both were standardized by NIST, but they are different designs, not successive versions of the same algorithm.

SHA-2 / SHA-512 Keccak / SHA-3
Standardized 2001 (FIPS 180-2) 2015 (FIPS 202), after the NIST competition won by Keccak in 2012
Construction Merkle–Damgård with a compression function Sponge construction (absorb / squeeze) over the Keccak-f permutation
Length extension Plain SHA-512 is vulnerable, which is why HMAC is used for keyed use Not vulnerable by design
Role in this pipeline SHA-256 in the BIP-39 checksum; HMAC-SHA512 in BIP-32; PBKDF2-HMAC-SHA512 for the seed Keccak-256 for the address and for EIP-55

Keccak-256 ≠ SHA3-256. Ethereum adopted Keccak before NIST finalized SHA-3. When NIST published the standard it changed the padding/domain-separation byte (0x06 for SHA3-256 instead of the original 0x01). The internal permutation is the same, but the two functions give different outputs for the same input, so a library must expose the original Keccak-256 to compute Ethereum addresses correctly.

5. Why Several Techniques Instead of One Algorithm?

No single algorithm can do all these jobs: each primitive solves a different problem with different requirements (randomness, determinism, reversibility, speed, human usability). Combining them keeps each part simple, replaceable and independently analyzable.

  • BIP-39 / BIP-32 / BIP-44 → key management and derivation. They let a user back up one short secret and recover unlimited keys and accounts, in the same way across different wallets. They are about convenience and interoperability, not about signatures.
  • secp256k1 → public/private key relationship and digital signatures. Only an asymmetric scheme lets anyone verify a signature without learning the secret. A hash function alone cannot provide this.
  • Keccak-256 → hashing. It shortens the 64-byte public key into a compact 20-byte address and adds a layer of indirection: the address does not directly reveal the public key until the account signs a transaction.
  • EIP-55 → checksum / error detection. It is purely a safeguard against human typos. It adds no security against attackers and, being only a case pattern, needs no change to the protocol.

In short: derivation manages secrets, public-key crypto proves ownership, hashing produces compact identifiers, and checksums protect people from mistakes.

6. Historical Context & Timeline

  • 1977: RSA, the first widely adopted public-key cryptography.
  • 2001: Standardization of SHA-2 (including SHA-512) by NIST.
  • 2012: Introduction of BIP-32 (HD wallets) and the Keccak win in the competition for the SHA-3 standard.
  • 2013: Introduction of BIP-39 (mnemonic sentences).
  • 2014: Standardization of BIP-44 (multi-account paths).
  • 2015: Official standardization of SHA-3 (FIPS 202) and launch of the Ethereum network.
  • 2016: Introduction of EIP-55 (Ethereum mixed-case checksum addresses).

7. Statistical Properties & Test Vector

  • Entropy and Seed: If the entropy is uniform, the mnemonic phrase maps uniformly over the space of possibilities (2128 or 2256). The seed resulting from PBKDF2 is statistically indistinguishable from a random string.
  • Keccak Avalanche: Flipping a single input bit changes about 50% of the output bits. Over the 160 bits of an Ethereum address, roughly 80 bits are expected to change abruptly.
  • EIP-55 Robustness: The uppercase/lowercase pattern offers protection against random typing errors, with an estimated residual error probability of around 0.003% (2-15).
